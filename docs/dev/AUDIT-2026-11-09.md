# COre audit: baseline v10.3.0 (`b84d355`), 2026-11-09

Method: fetched `origin/main` (= `b84d355`, clean tree), read every subsystem's code, queried GitHub
(releases, tags, Actions runs and job logs) with `gh`, ran `npm test` / `npm run check`, plus earlier
real-Electron runs in this environment. "Confirmed" means reproduced or proven from logs or code paths.
"Probable" means strong code evidence, not yet reproduced.

## Critical

### C1. Every release build has failed, and every published release is broken (confirmed)
- **What happens:** All 12 "Windows installer" runs (v2.0.0 → v10.3.0) ended in `failure`. electron-builder runs two
  GitHub publishers concurrently ("publishing … publishing", "creating GitHub release" twice in the log). Both
  try to create the release, the second gets `422 Validation Failed`, and the job aborts. Each release kept
  whichever single upload finished first: v2.0.0, v4.0.0, v7.0.0, v10.0.0 and v10.2.0 contain **only
  `COre-Setup-x.exe.blockmap` (no installer)**. The others contain only the `.exe`. **No release has `latest.yml`.**
  v10.3.0 failed earlier (504 gateway timeout) and has no release.
- **Why it matters:** Users following the README get no installer for half the versions. The packaged
  auto-updater (electron-updater) needs `latest.yml`, so installed copies can never update.
- **Evidence:** `gh api …/releases` (assets per tag); job log of run for `4988642` (422 after the double
  "creating GitHub release"); `.github/workflows/release.yml:43` (`--publish always`); `package.json` `build.publish`.
- **Verify:** `gh api repos/rawsushies/core-ai-companion/releases --jq '.[] | [.tag_name, (.assets|map(.name)|join(","))]'`.
- **Repair:** Build with `--publish never`, then create the release (as a **draft**) and upload the exe,
  blockmap, `latest.yml` and SHA256SUMS in one controlled step after the gates pass.
- **Regression risk:** Low for the code. The existing broken releases need a human decision (delete them or
  mark them pre-release), so they're in the approval queue.

### C2. Version bump on main publishes a public release, and tests don't gate it (confirmed)
- **What happens:** `release.yml:5-9` triggers on any push to `main` touching `package.json`.
  `release.yml:41` has `continue-on-error: true` on `npm test`, and `npm run check` never runs in CI. There is no
  CI for branches or PRs.
- **Why it matters:** Unverified code reaches users. This violates the new release policy.
- **Repair:** Separate `ci.yml` (branches + PRs; Ubuntu + Windows; check + test blocking; packaged smoke).
  `release.yml` runs only on an explicit `v*` tag (or manual dispatch), verifies tag == package.json version,
  re-runs all gates, smoke-tests the packaged app and the installer, and creates a **draft**.

### C3. Installed copies would reject unsigned updates (probable)
- **What happens:** `package.json:66` sets `win.signtoolOptions.publisherName`, but builds are unsigned ("no code
  signing certificate configured, signing is skipped" in every log). electron-updater writes `publisherName`
  into `app-update.yml` and verifies the downloaded installer's Authenticode publisher against it. An unsigned
  update fails that check.
- **Repair:** Only set `publisherName` when a certificate is configured. Document the signing path.
- **Verify:** Needs a Windows install → update cycle. **Not verifiable here** (Linux sandbox, no Windows runner access).

## High

### H1. Corrupt `config.json` silently replaced with defaults: data loss (confirmed)
- **What happens:** `config.js:139-145` returns defaults on a parse error, then `loadConfig` calls `cfg.save()`
  (`config.js:164`), overwriting the user's file, including encrypted API keys, hotkeys and the calendar link.
- **Repro:** Write `{"voice": {` into `config.json`, start COre. The file now holds defaults.
- **Repair:** On a parse failure, move the bad file to `config.json.corrupt-<time>`, start with defaults, and
  tell the user where their old file is. Same for `state.json`.

### H2. Corrupt `memory.json` / `notes.json` wiped on the next save (confirmed)
- `memory.js:32-35` and `skills.js:146` swallow parse errors and start empty. The next `remember()` or `note`
  overwrites the file. `skills.js:151` (Notes) writes non-atomically, so a crash mid-write corrupts the file.
- **Repair:** The same quarantine approach; atomic writes for notes; keep a rolling backup of memory.

### H3. Source updater: no rollback, follows `main` HEAD, no integrity anchor (confirmed by code)
- `updater.js:160-164` + `_applyZip` (`updater.js:184-200`) prune and copy over the running install in place.
  An error midway (disk full, AV lock, EBUSY on Windows) leaves a half-updated, possibly unbootable app with no
  backup. There's no crash-loop detection after an update.
- It updates from `refs/heads/main` (`updater.js:148,185`), so every merge to main deploys to every source
  install within 6 h, bypassing any release gate. The version is read from `raw…/main/package.json`, then the
  zip is fetched separately (TOCTOU: they can differ).
- `npm install` runs after updates (`updater.js:180`), executing dependency lifecycle scripts. That's inherent to
  source installs, but worth documenting.
- **Repair:** Default channel = latest **published GitHub release tag**, downloading that tag's zip and checking
  that its package.json version equals the tag. Back up `src/`, `assets/`, `package*.json` before applying,
  restore on any error, and restore automatically if the updated app fails to start twice (crash-loop
  rollback). Keep the `main` channel opt-in for developers.

### H4. Windows Claude CLI path untested in CI (confirmed)
- `test/claude.test.js:56,90,107,120,133` skip on `win32`: the 5 ClaudeCli process tests (persistent session, stale
  session, Stop/restart, login errors). The Windows spawn (`.cmd` shim via shell, `forWindowsShell` quoting) has
  never run under test. CI logs show `# skipped 9`.
- **Repair:** Add a Windows-compatible fake CLI (a `.cmd` wrapper around the Node fixture) and run these tests on Windows.

## Medium
- **M1. Calendar:** `TZID` ignored (times in a named zone read as local), `RRULE` recurring events ignored,
  `EXDATE` ignored (`skills.js:117-130`). Recurring meetings, the most common kind, don't show.
- **M2. Calendar feed URL is a credential stored in plain text** in `config.json` (`config.js:91`), unlike API
  keys (safeStorage, `main.js:205-212`). It's sent to the settings renderer as a normal value.
- **M3. `uncaughtException` handler swallows all main-process errors** (`main.js:68`). COre keeps running in a
  possibly inconsistent state, with no restart offer and no user notice.
- **M4. Memory:** near-duplicate merge exists (`memory.js:47-61`), but there's no source (which conversation or
  provider), no contradiction handling ("I live in Jakarta" vs "I live in Bandung" both kept), no project
  scoping, no backup.
- **M5. Provider streaming:** fallback happens only before the first token (`brain/index.js`). A stream that
  dies midway leaves a truncated reply with no retry. There's a single 240 s turn timeout (`claudeCli.js:16`),
  no per-token idle timeout, and context management is left entirely to each provider.
- **M6. Watch mode** enumerates all windows via `desktopCapturer` every 8 s (`watch.js:56`). Cost on Windows is
  unmeasured.
- **M7. Release updater** downloads 250 MB installers automatically (`releaseUpdater.js:12`) on any connection,
  including metered ones. Acceptable, but undocumented.

## Low
- **L1.** Test hooks in production code (`main.js:2190,2193`, `CORE_DEBUG_*`). Harmless, but untidy.
- **L2.** `asar: false` (larger installer, slower install). Intentional for worker and model paths, but undocumented.
- **L3.** Actions pinned by tag (`@v4`), not by SHA.
- **L4.** The settings reset monkey-patches `config.save` / `state.set` (`main.js` reset action). Works, but fragile.

## Documentation inconsistencies
- README: "Installed copies update themselves from Releases" and "Download COre-Setup-x.y.z.exe": false today (C1, C3).
- RELEASE_NOTES.md is for 10.0.0; the current version is 10.3.0.
- ROADMAP marks everything shipped; it has no post-10 direction (Meiosis, task engine, reliability).
- README describes source updates "from main". That will change with H3.

## Missing tests and untested critical paths
- `src/main/main.js` (2232 lines): IPC handlers, clone lifecycle, settings apply, skill chaining. No unit
  tests, only manual or real-Electron runs.
- Release updater (packaged), source updater apply/rollback, installer/uninstaller: no automated tests at all.
- Overlay renderer (`app.js`, gestures and shapes in context): browser-demo smoke only.
- Windows: no packaged smoke test, no installer test, Claude CLI tests skipped.

## Verified as sound (no action)
- Markdown rendering is `textContent`-only (`dock/md.js:2`); no XSS from model output.
- Strict CSP on every window (`default-src 'self'; script-src 'self'`), sandboxed renderers, `contextIsolation`,
  navigation and popups blocked (`main.js:61-65`), IPC sender checks on every channel family.
- Persistent Claude session runs with `--tools ""` (`claudeCli.js:183`); the per-message fallback allows only
  `Read`; no `--dangerously-skip-permissions`.
- Skills: fixed app list and media keys, click-to-open links, https-only plugin templates (`skills.js`).
- Helper processes are stopped on quit and restart (fixed in 10.3.0, verified: 4 → 0 processes).
- Config writes are atomic (`config.js:151-156`).

## Risks to user data
- H1/H2 (silent overwrite) are the main risks. Uninstall keeps app data (`deleteAppDataOnUninstall: false`).
  Reset intentionally deletes config, state, memory, notes and workspace (and says so).
